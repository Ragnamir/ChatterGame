# Требования к платформе словесных игр

Статус: заморожено по итогам раунда обсуждения. Изменения только через `DECISIONS.md`
записью с `supersedes D-xxx`. Агент не дополняет требования домыслом: если случая нет
в документе, он задаёт вопрос, а не выбирает.

---

## 1. Контекст

Платформа для проведения нарративных словесных игр. Фактически — набор чатов
с дополнительной информацией о мире. Мастер вручную управляет нарративом, уровень
автоматизации механик намеренно минимальный (`D-011`).

Целевой масштаб: 4–6 игроков (до 10), 10–50 локаций, длительность около месяца,
асинхронный темп с перерывами в дни. Это определяющее требование: оно делает
восстановление сессии важнее скорости, а читаемость истории важнее новизны.

## 2. Технологический контур

| Слой | Выбор | Примечание |
|---|---|---|
| Backend | Java 21, Spring Boot 3.x, Gradle Kotlin DSL | package-by-feature монолит |
| БД | PostgreSQL 16 | единственный магазин состояния |
| Миграции | Liquibase, YAML changelogs | одна на этап, применённые не правятся |
| Реалтайм | Spring WebSocket, без STOMP | собственные JSON-события |
| Аутентификация | серверная сессия, HttpOnly cookie | не JWT (`D-073`) |
| Пароли | Argon2id | |
| Медиа | файловая система | whitelist растровых форматов (`D-074`) |
| Frontend | см. `D-090` (не подтверждён) | PWA, ставится как приложение |
| Тесты | JUnit 5, Testcontainers, AssertJ | реальный Postgres, не H2 |

## 3. Глоссарий

| Термин | Значение |
|---|---|
| Игра | контейнер мира: чаты, переходы, персонажи, предметы, сообщения |
| Мастер | единственный субъект, изменяющий мир |
| Участие | связь пользователь ↔ игра с ролью и статусом |
| Персонаж | внутриигровой субъект; игрок его занимает |
| Присутствие | нахождение персонажа в локационном чате |
| Скрытность | состояние персонажа: невидим для других игроков |
| Хранилище | самостоятельная сущность, содержащая предметы (`D-016`) |
| Inbox | материализованная видимость события для конкретного персонажа |
| Тетрадь | личная панель игрока: заметки и сохранённые сообщения |
| Change set | типизированный список операций над объектами игры |

## 4. Состояние игры

Три независимые оси плюс флаг (`D-003`).

| Ось | Значения | Смысл |
|---|---|---|
| `readiness` | `DRAFT` / `READY` | контент достроен, можно входить |
| `visibility` | `PUBLIC` / `PRIVATE` | вход свободный или по приглашению |
| `phase` | `NOT_STARTED` / `RUNNING` / `FINISHED` | можно ли играть |
| `paused` | `true` / `false` | мастер отсутствует осознанно (`D-059`) |

Правила переходов:

- `DRAFT → READY`: требуется пройти валидацию готовности (п. 20). Откат `READY → DRAFT`
  возможен только в `phase = NOT_STARTED`.
- `NOT_STARTED → RUNNING`: требует `READY`. Необратимо.
- `RUNNING → FINISHED`: по действию мастера. Необратимо. Все чаты сохраняются в состоянии
  на момент конца и остаются читаемыми. Создаётся чат финального обсуждения, туда
  переносятся все персонажи, там разрешён только тип `JOKE`.
- `paused` устанавливается и снимается только мастером, в любой `phase` кроме `FINISHED`.
  Не влияет на права, только на отображение причины ожидания.

Запрещённые комбинации проверяются на сервисе, а не в БД-чек-констрейнте, потому что
текст ошибки важен для UI мастера.

## 5. Пользователь и аутентификация

- Регистрация по логину и паролю. Емейл не обязателен для входа, но нужен для
  подтверждения и сброса (`D-078`).
- Логин: кириллица допустима. Уникальность и сравнение по NFC-нормализованному
  нижнему регистру, посчитанному сервером (`D-080`).
- Профиль пользователя: отображаемое имя, аватар, настройки темы, ключи LLM (п. 19),
  предпочтения уведомлений (заготовка, `D-070`).
- `auth_identity(provider, provider_user_id, email, verified_at, user_id)` —
  единственная таблица креденшалов. Сейчас только `provider = LOCAL`. Google и VK
  добавляются строками без миграции пользователей.
- Правило слияния при будущей OAuth-привязке: подтверждённый емейл добирает локальный
  аккаунт, неподтверждённый создаёт новый с требованием подтверждения (`D-078`).
- Подтверждение емейла в профиле `dev` проставляется автоматически, отправка — в лог.
  Профиль `prod` падает на старте без настроенного SMTP (`D-079`).
- Сброс пароля: одноразовый токен, в БД хеш, TTL 30–60 минут, инвалидация при
  использовании и смене пароля, rate limit, одинаковый ответ на существующий и
  несуществующий емейл.

## 6. Участие в игре

Роль одна из: `MASTER`, `PLAYER`, `OBSERVER`. Один пользователь может иметь несколько
участий в одной игре? Нет: участие уникально по `(user, game)`, роль одна.

Статусы участия: `INVITED`, `JOINED`, `LEFT`, `BANNED`.

- `MASTER` — создаёт игру, автоматически `JOINED`.
- `OBSERVER` — read-only. Видит открытую часть игры и персонажей, видит чаты.
  Не видит закрытые истории, личные диалоги, заметки, скрытых персонажей и неизвестные
  переходы (`D-063`). У наблюдателя нет персонажа, поэтому его видимость материализуется
  строками `inbox_entry` с субъектом-участием (`D-086`): при входе в середину игры
  выполняется backfill исторических строк по всему открытому на этот момент содержимому.
  Без этого либо нарушается `D-030` (чтение мимо `inbox_entry`), либо опоздавший
  наблюдатель получает пустые комнаты, что делает участие бессмысленным.
- `BANNED` — мастер запретил участие в конкретной игре. Не глобальный бан.
  Это статус участия, а не вид `restriction` (§13).
- Мастерство не передаётся (`D-021`).

## 7. Чаты

### 7.1 Локационный чат

Соответствует месту. Поля: название, описание (`например: «Таверна Козлоногий Урод»` /
`«Неказистое заведение с дешёвым алкоголем и спившимися завсегдатаями»`), картинка,
флаг архивации.

- Персонаж присутствует или нет. Присутствующий читает и пишет, отсутствующий не
  получает сообщений и не может писать.
- Персонаж может присутствовать скрытно: другие игроки не видят ни его, ни его сообщений.
- Мастер видит все локационные чаты всегда.
- После `READY` удаление запрещено, только архивация (`D-009`).

### 7.2 Радиочат (чат связи)

Моделирует радио или волшебную связь. Поле: название.

- Связывает фиксированных персонажей, список задаёт мастер.
- Разрешён только тип `SPEECH` (`D-039`).
- Мастер может отключить чат в рамках игры.
- Участники не обязаны присутствовать в одной локации.

### 7.3 Личный чат с мастером

- Создаётся автоматически для каждого `PLAYER`, привязан к участию, не к персонажу (`D-037`).
- В UI игрока подписан «Мастер», в UI мастера — именем персонажа (по последнему выбранному
  или по явному указанию игрока).
- Игрок может писать от лица любого своего персонажа; выбор влияет только на подпись в ленте.
- Бюджет пошагового режима не расходует (`D-013`).
- Не доступен `OBSERVER`.

### 7.4 Шёпот

Многосторонний приватный канал (`D-038`).

- Создание: приглашение и согласие участников.
- Требования к участникам в момент приглашения: та же локация, тот же статус скрытности,
  разрешение говорить.
- Живёт, пока не закрыт участником или мастером. Уход из локации не разрывает.
- Мастер состоит по умолчанию и видит ленту.
- Тип `JOKE` разрешён по умолчанию.

### 7.5 Чат финального обсуждения

Создаётся при `RUNNING → FINISHED`, единственный на игру, принимает всех персонажей,
разрешает только `JOKE`.

## 8. Переходы между локациями

- Фиксированные, создаёт мастер, направление — явное (ориентированные рёбра;
  симметричность задаётся мастером двумя рёбрами, если нужно).
- Состояние видимости для конкретного персонажа: `UNKNOWN` (не отображается),
  `KNOWN_UNAVAILABLE` (отображается с причиной, например «переход недоступен из-за бури»),
  `AVAILABLE`.
- Мастер открывает и закрывает переходы в любой момент, включая ход игры; причина —
  свободный текст.
- Перемещение возможно только по `AVAILABLE` переходу, кроме мастера, который
  перемещает кого угодно куда угодно всегда.
- После `READY` удаление переходов запрещено (`D-009`).

Знание перехода привязано к персонажу, а не к игроку: два персонажа в одной локации
могут знать разные переходы.

## 9. Персонажи

Создаёт только мастер (`D-020`). Поля:

| Поле | Видимость |
|---|---|
| Имя | всем, кому виден персонаж |
| Картинка (портрет) | всем, кому виден персонаж |
| Описание внешности | всем, кому виден персонаж |
| Открытая история | всем игрокам игры |
| Закрытая история | только играющему игроку и мастеру |
| Хранилище мелкое (`character_hidden`) | только владельцу и мастеру |
| Хранилище крупное (`character_visible`) | всем, кому виден персонаж (`D-017`, `D-019`) |
| Признак играбельного | техническое |
| NPC / играемый | техническое |

Поведение:

- Стартовое размещение в локационных чатах задаёт мастер.
- Занятость: играемого занимает один игрок одновременно; NPC не занят никем, но
  мастер может писать от его лица (`D-004`).
- Скрытность: вход только с разрешения мастера, выход — свободный у игрока и мастера (`D-006`).
  При скрытии после публичных действий персонаж отображается как ушедший, прошлые
  реплики остаются (`D-007`).
- Мастер редактирует описание и инвентарь в любой момент, обновление у игроков мгновенное.
- Ограничения (п. 13) навешиваются на персонажа: запрет речи, запрет действия, запрет шутки.
- Освобождение персонажа возможно мастером в любой момент (`D` в п. 20 — валидация готовности).

## 10. Хранилища и предметы

Хранилище — самостоятельная сущность (`D-016`) с типом:

| Тип | Видимость содержимого |
|---|---|
| `LOCATION` | всем присутствующим в локации |
| `CHEST` | всем присутствующим в локации, где стоит сундук; описание сундука видно, содержимое — после открытия |
| `CHARACTER_HIDDEN` | только владельцу и мастеру |
| `CHARACTER_VISIBLE` | всем, кому виден владелец (`D-019`) |

Предмет: название, описание, картинка, признаки (крупный/мелкий — определяет, в каком
хранилище может лежать), произвольные текстовые свойства.

Правила перемещения:

- Операция атомарна с блокировкой строки предмета; проигравший в гонке получает
  системное событие «предмет уже забран» (`D-015`).
- Игрок берёт из чужого `CHARACTER_VISIBLE` только с разрешения владельца, выраженным
  действием в игре; из `CHARACTER_HIDDEN` — никогда.
- Передача между персонажами требует одинаковой скрытности (`D-018`) и присутствия
  в одной локации.
- Мастер перемещает всегда и без ограничений.
- Игроки могут передавать предметы друг другу в одном локационном чате — единственное
  исключение из «мир меняет только мастер».

## 11. Сообщения

Пять типов (`D-031`):

| Тип | От чьего имени | Бюджет хода | Назначение |
|---|---|---|---|
| `SPEECH` | персонаж | 1 на ход | речь |
| `ACTION` | персонаж | 1 на ход | описание действия |
| `JOKE` | персонаж | нет | метагейм, не относится к игре |
| `MASTER` | мастер | нет | событие мира, не от персонажа |
| `SYSTEM` | система | нет | вход/выход, правки, переходы, выдача, ход (`D-031`) |

Матрица прав на запись (`assertCanPost`, `D-065`):

| Тип | PLAYER | MASTER | OBSERVER |
|---|---|---|---|
| `SPEECH` | свой занятый персонаж, присутствующий в чате, без запрета речи, игра `RUNNING` | любой присутствующий в чате персонаж (`D-004`) | нет |
| `ACTION` | свой занятый персонаж, присутствующий, без запрета действия | любой присутствующий | нет |
| `JOKE` | свой занятый персонаж, присутствующий, без запрета шутки | любой присутствующий | да, в чате финального обсуждения |
| `MASTER` | нет | да, в любом чате игры | нет |
| `SYSTEM` | нет | нет (генерирует система) | нет |

Дополнительные ограничения:

- В радиочате разрешён только `SPEECH`.
- В чате финального обсуждения разрешён только `JOKE`.
- Личный чат с мастером: `SPEECH`, `JOKE` от любого своего персонажа; бюджет не расходует.
- В пошаговом режиме лимит суммарный по всем чатам, кроме личного (`D-013`).
- Сообщение мастера от лица персонажа расходует бюджет персонажа и помечается
  `on_behalf_of_master` (`D-005`).

Видимость:

- Отзыв невозможен (`D-008`).
- При переходе в локацию персонаж получает только последнее сообщение чата (`D-032`).
- При восстановлении сессии доставляется всё неполученное с момента последнего ack (`D-032`).

## 12. Видимость и доставка

- Журнал `game_event` — append-only, единственный источник истины (`D-033`).
- При записи события вычисляется набор получателей и материализуются строки `inbox_entry`
  per персонаж (`D-030`).
- Субъект получения — `inbox_entry(subject_kind, subject_id, chat_id, event_seq)`, где
  `subject_kind ∈ {CHARACTER, MEMBERSHIP}` (`D-086`). Персонажи получают строки для
  игрового контента, участия-наблюдатели — для открытого контента. Read-путь для обоих
  случаев единый, иначе `D-030` обходится отдельным фильтром для наблюдателя.
- Курсор прочтения: `(subject_kind, subject_id, chat_id, last_seq)`.
- Подписка двухуровневая: игровой канал несёт `{chat_id, seq, kind}` и счётчики,
  канал открытого чата несёт тела (`D-035`). Мета-событие не содержит фрагмента текста
  и имени говорящего.
- Счётчики непрочитанных выводятся из `inbox_entry` (`D-036`), поэтому бейдж сам по себе
  не учитывает скрытых персонажей и чужие личные каналы.
- Resume: клиент присылает `last_seq` по подпискам, сервер одним запросом догружает
  недостающее по индексу `(subject_kind, subject_id, chat_id, seq)` (`D-083`).
- Фан-аут за интерфейсом `Fanout` с реализациями `InJvmFanout` и `PostgresNotifyFanout` (`D-084`).
- Шардирование по `game_id`: одна игра целиком на одном инстансе (`D-072`).
- Heartbeat обязателен; мёртвые сокеты высвобождаются по таймауту, а не по TCP.

## 13. Ограничения

`restriction(game, subject_kind, subject_id, kind, reason, created_by, created_at,
expires_at, revoked_at)` (`D-064`).

Виды: `NO_SPEECH`, `NO_ACTION`, `NO_JOKE`, `NO_MOVE`. Запрет вступления в игру сюда не
входит: это статус участия `BANNED` (§6), а не ограничение персонажа.

- Это отражение игровой ситуации (сон, пленение, потеря голоса, абьюз шутками),
  а не наказание; поэтому причина обязательна, а снятие — штатная операция мастера.
- Срок действия поддерживается, но не обязателен.
- Проверка на каждое событие (`D-065`), состояние читается из БД, не кэшируется в сокете.

## 14. Пошаговый режим

Флаг игры `turn_based` (`D-012`), включается и выключается мастером в любой момент.

Сущности:

- `turn(game, n, opened_at, closed_by, closed_at, status)` — единственная обязательная
  механика времени в проекте (`D-011`).
- `turn_budget(turn, character, action_used, speech_used)`.

Правила:

- Лимит: 1 `ACTION` + 1 `SPEECH` на персонажа за ход, суммарно по всем чатам, кроме
  личного с мастером (`D-013`).
- `JOKE`, `MASTER`, `SYSTEM` лимит не расходуют.
- Сообщение мастера от лица персонажа расходует лимит персонажа (`D-005`).
- Смена хода сбрасывает лимиты; несовершённые действия сгорают, новый ход не зависит
  от прошлого (`D-012`).
- Мастер открывает ход всем сразу; точечное продвижение в рамках механики невозможно —
  для этого служат ограничения (`D-012`).
- При неоткрытом ходе дольше N часов: UI показывает «ожидание мастера», `SPEECH` и
  `ACTION` запрещены, `JOKE` и шёпот разрешены, ничего не сгорает (`D-060`).

## 15. Тетрадь

Одна панель с двумя вкладками, две таблицы (`D-055`).

### 15.1 Заметка

`note(author_membership, target, body)` + `note_keyword(note, raw, normalized, exact_match)`.

- `target`: конкретный персонаж или мастер. Автор: мастер (для указанных персонажей
  и для себя), игрок (только для своих персонажей).
- Совпадение вычисляется один раз при записи сообщения, результат — `matched_note_ids` (`D-050`).
- При создании или правке заметки существующие сообщения целевого субъекта досчитываются
  асинхронной задачей, область пересчёта — `inbox_entry` этого субъекта, во время пересчёта
  у заметки стоит признак `matching_pending` (`D-087`).
- Лемматизация по-русски (Snowball), обязательная граница слова, флаг точного совпадения
  для имён (`D-051`).
- При конфликте ключей показываются все заметки списком (`D-052`).
- У игрока с несколькими персонажами — объединение с маркером владельца (`D-053`).
- Мастер видит заметки игроков (`D-054`).
- Наблюдателю заметок нет (`D-063`).

### 15.2 Сохранённое сообщение

`saved_message(owner_membership, message_id, text_snapshot, speaker_snapshot, comment, note_id)`.

- Привязка к игроку (участию), не к персонажу: мета-инструмент, при смене персонажа остаётся.
- Хранится ссылка и снимок текста; изменение данных говорящего мастером приемлемо,
  но снимок защищает запись от молчаливой правки (`D-055`).
- Наблюдателю доступно (это свойство игрока, `D-063`).

## 16. Журнал событий

`game_event(id, game_id, seq, type, chat_id, actor_user_id, character_id,
on_behalf_of_master, payload jsonb, created_at)`, уникальный `(game_id, seq)`.

- `seq` выдаётся в транзакции мутации через блокирование счётчика потока игры
  (`SELECT ... FOR UPDATE` на строке `game_stream`); при 4–10 игроках конкуренция тривиальна.
- Из журнала собираются: рассылка, аудит, resume клиента, экспорт (`D-033`).
- Все мутации мира — через `GameMutationService` с сериализацией per-game (`D-034`).
- Payload не содержит закрытых историй и содержимого личных диалогов в открытом виде
  для сторонних читателей; доступ к чтению журнала — по правам участия.
- Хранение не ограничивается (`D-071`).

## 17. Change set и заявки

Единая сущность `request(id, game_id, origin, type, from_membership, to_character_id,
payload jsonb, status, error, idempotency_key, expires_at)` (`D-040`).

`origin ∈ {MASTER, PLAYER, LLM}`, `status ∈ {PENDING, RUNNING, SUCCEEDED, FAILED, APPROVED, REJECTED, PARTIALLY_APPROVED, EXPIRED}`.

Типы заявок:

- `CHARACTER_EDIT` — предложение правки полей персонажа (внешность, открытая история,
  закрытая история, инвентарь). Игрок не применяет, а предлагает; мастер видит диффом.
- `ROLE_REQUEST` — просьба о персонаже под концепцию («хочу того, кто умеет в медицину»).
- `SLOT_QUESTION` — вопрос о слоте.
- `CO_MASTER` — вызов со-мастера, payload ответа = change set.
- `AUTOPILOT` — вызов автопилота, payload ответа = реплика или действие.

Машина применения: частичное одобрение по операциям, атомарное применение каждой,
старое значение остаётся в журнале, откат возможен. Невалидная схема payload = `FAILED`,
частичное применение мусора запрещено (`D-041`, `D-043`).

Поле «пожелания по отыгрышу» при занятии персонажа: свободный текст до нескольких
сотен знаков, материал мастеру, не канон.

## 18. LLM

- Используется ключ, указанный мастером; без ключа опции LLM недоступны целиком (`D-042`).
- Со-мастер: получает свой промпт-набор правил, тексты игры и запрос мастера; возвращает
  change set предложений.
- Автопилот: вызывается мастером за отсутствующего игрока; получает тексты игры и всю
  информацию, доступную персонажу (включая его заметки, `D-046`); возвращает реплику или
  действие; мастер обязан одобрить.
- Оценка итогов: полный текст игры и история каждого персонажа.
- Контекст иерархически сжимается (`D-045`).
- Не отдаётся провайдеру: закрытые истории чужих персонажей, личные диалоги игроков
  с мастером (`D-046`).
- Технический контракт: вызов строго вне транзакции (`D-044`), отдельный bounded executor,
  один одновременный запрос на игру, таймаут, классификация ошибок, статус в БД,
  идемпотентный ключ (`D-043`).

## 19. Медиа

- Файловая система, whitelist `jpeg, png, webp, gif`; SVG и HTML запрещены (`D-074`).
- Имя ассета — UUID, доступ на GET с проверкой участия в игре (`D-075`).
- Лимит 2–5 МБ на файл, 4096 px на сторону, проверяется при декодировании (`D-076`),
  100–200 МБ на игру, лимит одновременных загрузок на пользователя.
- ORPHAN-сборка по «не упомянут ни в одной живой сущности»; замена атомарная;
  EXIF вырезается; отдача с `nosniff`, точным `Content-Type` и долгим `Cache-Control` (`D-077`).
- Ассеты архивированного персонажа живут, пока жива игра (`D-077`).

## 20. Жизненный цикл и эксплуатация

Валидация готовности `DRAFT → READY` (`D-009`):

- Блокирующее: играбельный персонаж без размещения; предмет вне хранилища; переход в
  несуществующую локацию; радиочат менее чем с двумя участниками.
- Предупреждающее: локация без описания; персонаж без портрета; недостижимые локации;
  NPC вне хранилищ и локаций.
- Флаг `READY` остаётся за мастером: он может объявить готовность с предупреждениями.

Отсутствие мастера (`D-058`):

- Пауза с причиной (`D-059`), таймаут хода (`D-060`), экспорт полного комплекта (`D-061`),
  никогда не удалять (`D-010`).
- Помощник с ограниченными правами — отложено, требует согласия мастера по каждой игре (`D-062`).

Финал: `RUNNING → FINISHED` переносит персонажей в чат финального обсуждения, все
остальные чаты остаются читаемыми в состоянии на момент конца.

## 21. Нефункциональные требования

- Видимость материализована при записи; фильтрация на чтении запрещена (`D-030`).
- Права проверяются на каждое событие (`D-065`).
- Виртуализация списков и пагинация — до первой фичи фронта (`D-082`).
- Индекс `(subject_kind, subject_id, chat_id, seq)` с первой миграции; resume одним
  запросом (`D-083`).
- Никаких блокирующих внешних вызовов в транзакции (`D-044`).
- Логи структурированные, с `game_id` и `event_seq`, без текста сообщений (`AGENTS.md`).
- Аудит: кто, когда и что изменил в мире — читается из журнала событий отдельно.
- UI только русский, через ключи интернализации (`D-081`); клавиатурная навигация по чатам (`D-085`).
- PWA: установка как приложения, офлайн-чтение кэшированной ленты, service worker.
- Пуш отложен; существуют только journal с последовательностью, inbox с курсором и
  `notification_preference` с картой «событие → канал» (`D-070`).

## 22. Вне объёма

- Механики: характеристики, здоровье, броски, кубики, инициатива, эффекты со сроком
  действия (`D-011`).
- Передача мастерства (`D-021`), ограниченный помощник (`D-062`).
- Пуш-уведомления и нативная обёртка (`D-070`).
- Генерация персонажей игроками, анкеты, автоприём (`D-020`).
- Отзыв сообщений (`D-008`), физическое удаление (`D-010`).
- OAuth Google и VK — на последнем этапе, модель данных готова (`D-078`).
- Мультиязычность UI (`D-081`).
- Монетизация, донат, платные игры.

## 23. Что проверяется в первую очередь

Три артефакта обнаруживают оставшиеся дыры дешевле всего:

1. Схема БД (миграция каркаса) — проверяет, что все сущности и их связи помещаются.
2. Контракт WebSocket-событий с перечнем типов `SYSTEM` — проверяет, что пяти классов
   сообщений хватает и что мета-событие не утекает содержимым.
3. Матрица прав из п. 11 и матрица видимости из п. 12 в виде табличных тестов —
   проверяет скрытность, личные каналы, наблюдателя и пошаговый бюджет.
