# План реализации

Декомпозиция на атомарные этапы. Каждый этап имеет проверяемый автоматизированно результат,
следующий начинается только после зелёного гейта текущего и подтверждения владельцем продукта.

Требования — в `REQUIREMENTS.md`, обоснования — в `DECISIONS.md`. Этот документ отвечает
только на «в каком порядке и с какой проверкой».

---

## 1. Протокол гейта

Этап сдаётся, когда выполнены все пять пунктов:

1. `./scripts/gate.sh <STAGE>` завершается с кодом 0.
2. Внутри гейта: сборка, все тесты (включая тесты предыдущих этапов), проверка миграций
   на чистой БД и на даун-сценарии «применить предыдущую, затем текущую».
3. Добавленные тесты носят имя этапа (`E08VisibilityTest`), чтобы провал был адресным.
4. В `docs/STATUS.md` добавлена запись этапа: что сделано, что отклонено от плана, какие
   новые вопросы возникли.
5. Владелец продукта подтвердил результат. Без подтверждения этап не считается закрытым.

Скрипт гейта создаётся на `E01` и обязывает этап к наличию:

```
gate <STAGE>:
  build                  # ./gradlew clean build
  migrations             # Liquibase на чистой БД + diff с ожидаемым списком таблиц
  unit_and_integration   # Testcontainers, реальный Postgres
  contract               # сверка OpenAPI и схемы событий с зафиксированными снапшотами
  invariants             # глобальные инварианты проекта, см. п. 2
  stage_checks           # специфичные для этапа проверки, перечислены в его описании
```

Останавливать работу и спрашивать, а не обходить: противоречие между `REQUIREMENTS`
и `DECISIONS`, необходимость новой зависимости, необходимость менять применённую миграцию,
любой пункт, требующий решения владельца (пауза, экспорт, права наблюдателя).

## 2. Глобальные инварианты, проверяемые на каждом гейте

Эти проверки добавляются на `E01` и не отключаются никогда. Они ловят регрессию
архитектурных решений, а не функциональности.

| Инвариант | Проверка | Источник |
|---|---|---|
| Нет `DELETE FROM` по доменным таблицам игры | AST-анализ репозиториев | `D-010` |
| Каждая мутация мира порождает ≥1 событие `game_event` | интеграционный тест на список мутаций | `D-033` |
| Нет внешнего вызова внутри `@Transactional` | AST-анализ + `Detekt`-подобное правило | `D-044` |
| Чтение видимости только через `inbox_entry` | AST-анализ: запрет `JOIN message` без inbox в read-пути | `D-030` |
| Права через `assertCanPost`, а не кэш сокета | AST-анализ контроллеров и обработчиков событий | `D-065` |
| Все строки на русском через ключи i18n | скан фронтенда на кириллические литералы | `D-081` |
| Миграции только добавляются | сравнение хешей применённых файлов с манифестом | `AGENTS.md` |

## 3. Карта этапов

Три дорожки. `E` — домен и API, `F` — интерфейс, `O` — эксплуатация и доставка.
`F` и `O` идут параллельно с `E`, когда их зависимость зелёная.

| Этап | Название | Зависит от | Главная проверка |
|---|---|---|---|
| E01 | Скелет, БД, миграции, конвейер проверки | — | гейт работает и падает на намеренной поломке |
| E02 | Пользователь и локальная аутентификация | E01 | регистрация, вход, сессия, выход; прод падает без SMTP |
| E03 | Игра, участие, жизненный цикл, журнал событий | E02 | state machine + append-only журнал + аудит |
| E04 | Локационные чаты и переходы | E03 | граф переходов, три состояния видимости ребра |
| E05 | Медиа-ассеты | E03 | SVG отвергнут, бомба декомпрессии отвергнута, доступ по участию |
| E06 | Персонажи, присутствие, скрытность, перемещение | E04 | матрица скрытности и «отобразился как ушедший» |
| E07 | Хранилища и предметы | E06 | гонка за предмет: ровно один победитель |
| E08 | Сообщения: типы, права, материализованная видимость | E07 | полная матрица прав × видимость табличными тестами |
| E09 | Реалтайм: WebSocket, resume, двухуровневая подписка | E08 | resume после разрыва без потерь и дублей |
| E10 | Пошаговый режим | E09 | бюджет на персонажа суммарно по чатам |
| E11 | Личный чат с мастером, шёпот, радиочаты | E09 | условия создания шёпота, радио только речь |
| E12 | Тетрадь: заметки и сохранённые сообщения | E08 | лемматизация, конфликт ключей, слияние по игроку |
| E13 | Участие: приглашения, занятие, наблюдатели, пауза, архив | E08 | наблюдатель не видит закрытых данных |
| E14 | Change set engine и заявки игроков | E13 | частичное одобрение, атомарность, откат |
| F01 | Контур PWA: вход, список игр, кабинет | E03 | установка, вход, виден список игр |
| F02 | Игровая комната: ленты, переходы, мастер-панель | E09 | виртуализация, бейджи, клавиатурная навигация |
| F03 | Пошаговый режим и ограничения в UI | E10 | состояние «ожидание мастера» |
| F04 | Личные каналы и тетрадь | E11, E12 | подсветка ключевых слов, вкладки тетради |
| F05 | Заявки и панель мастера для LLM | E14 | дифф правок, частичное одобрение |
| O01 | Почта: подтверждение и сброс пароля | E02 | реальный SMTP, SPF/DKIM/DMARC чек-лист |
| O02 | Экспорт, архив, эксплуатационные операции | E13 | экспорт читается машиной и человеком |
| O03 | Заготовка уведомлений | E09 | таблица предпочтений + карта «событие → канал» |

Фазы:

- **Фаза 1 — каркас:** E01, E02, E03, F01. Результат: работающее приложение с входом
  и списком игр, доменная модель состояния игры проверена тестами.
- **Фаза 2 — мир:** E04…E07. Результат: мастер построил игру, в мире можно ходить
  и поднимать предметы.
- **Фаза 3 — играбельность:** E08, E09, F02. Результат: два клиента переписываются
  в реальном времени, скрытность и видимость работают.
- **Фаза 4 — управление ходом:** E10, E11, F03. Результат: полноценный стол, включая
  пошаговый режим и личные каналы.
- **Фаза 5 — мета:** E12, E13, F04, O02, O03. Результат: тетрадь, наблюдатели, пауза, экспорт.
- **Фаза 6 — интеллект:** E14, F05. Результат: заявки игроков и LLM на одном движке.

## 4. Детализация этапов

### E01 — Скелет, БД, миграции, конвейер проверки

Цель: существовать, собираться, применять миграции и падать на нарушенных инвариантах.
Ни одной доменной фичи.

Задачи:
1. Gradle (Kotlin DSL), Java 21, Spring Boot 3.x, package-by-feature (`user`, `game`,
   `chat`, `character`, `item`, `message`, `realtime`, `journal`, `media`, `note`,
   `request`, `llm`, `participant`).
2. `docker-compose.yml` с Postgres 16, профили `dev`/`prod`, отсутствие SMTP в `prod`
   роняет старт (`D-079`).
3. Liquibase: `db.changelog-master.yaml`, `changes/001-baseline.yaml` с каркасом всех
   таблиц из `REQUIREMENTS` (пустыми или с минимальными полями) — это проверяет, что
   модель данных помещается, до того как пойдёт код. UUIDv7 как PK, `BIGINT seq` для
   журнала, индексы `inbox (subject_kind, subject_id, chat_id, seq)` сразу (`D-083`, `D-086`).
4. Testcontainers-фикстура, OpenAPI-сниппет, `scripts/gate.sh` с пятью секциями из п. 1.
5. Проверки-инварианты из п. 2 как исполняемые правила, пока на пустом коде.
6. `docs/STATUS.md` с протоколом записи этапа.

Критерии приёмки: гейт зелёный; гейт краснеет, если вручную добавить `DELETE FROM message`
в репозиторий-заглушку; миграция применяется на чистой БД за один проход; повторный запуск
Liquibase ничего не меняет; список таблиц в БД совпадает со списком из п. 3.

Запрещено: контроллеры, сервисы, любая бизнес-логика.

### E02 — Пользователь и локальная аутентификация

Цель: войти и выйти, отличить `dev` от `prod`.

Задачи:
1. Таблицы `app_user`, `auth_identity`, `password_reset_token`.
2. Регистрация по логину и паролю, Argon2id, NFC-нормализация логина (`D-080`).
3. Серверная сессия, HttpOnly cookie, `SameSite=Lax`, выход, инвалидация сессии.
4. `MailSender` интерфейс + `LoggingMailSender` для `dev` (автоподтверждение) +
   валидация конфига для `prod` (`D-078`, `D-079`).
5. Сброс пароля: одноразовый хеш-токен, TTL, rate limit, одинаковый ответ на
   существующий и несуществующий емейл.
6. `GET /me`, обновление профиля и отображаемого имени.

Критерии приёмки: табличные тесты на нормализацию (`Вася`, `вася`, `ВАСЯ` — один аккаунт);
повторная регистрация тем же логином даёт 409 с одинаковым ответом; токен сброса
одноразовый и не переживает смену пароля; старт в `prod` без SMTP падает с внятной ошибкой;
пароли не появляются в логах (проверка сканом).

Запрещено: JWT, OAuth-таблицы сверх `auth_identity`, роли, эмэйл как логин.

### E03 — Игра, участие, жизненный цикл, журнал событий

Цель: создать игру, объявить готовой, запустить, завершить; всё через журнал.

Задачи:
1. Таблицы `game`, `membership`, `game_stream`, `game_event`.
2. `GameMutationService`: блокировка `game_stream` (`SELECT … FOR UPDATE`), выдача `seq`,
   запись события, применение эффекта. Единственная точка записи в доменные таблицы (`D-034`).
3. State machine по `REQUIREMENTS §4`: три оси плюс `paused`, таблица разрешённых переходов,
   отказ с текстом причины.
4. CRUD игры мастером: название, открытое и закрытое описание.
5. Участие: роли `MASTER/PLAYER/OBSERVER`, статусы `INVITED/JOINED/LEFT/BANNED`.
6. Валидация готовности: блокирующее и предупреждающее, `READY` возможен с предупреждениями.
7. Аудит-чтение: `GET /games/{id}/events` с пагинацией по `seq` и фильтром по типу.
8. Таблица `notification_preference` (заготовка, без отправки).

Критерии приёмки: каждый переход проверен табличным тестом «разрешён/запрещён» с проверкой
права; параллельные мутации одной игры дают непрерывный `seq` без дыр и дублей (тест на
10 потоков); любая мутация из списка оставляет событие (инвариант п. 2); `FINISHED`
необратим; удаление игры невозможно (`D-010`).

Запрещено: WebSocket, сообщения, персонажи.

### E04 — Локационные чаты и переходы

Цель: граф мест с управляемой мастером доступностью рёбер.

Задачи:
1. Таблицы `chat` (тип `LOCATION` в этом этапе), `transition`, `chat_state` (архивация).
2. CRUD локаций мастером: название, описание, флаг архивации.
3. Ориентированные переходы, состояния ребра `UNKNOWN / KNOWN_UNAVAILABLE / AVAILABLE`
   с текстом причины.
4. Мутации через `GameMutationService`, события `CHAT_CREATED`, `TRANSITION_OPENED`,
   `TRANSITION_CLOSED` как `SYSTEM`-заготовки.
5. Запрет удаления после `READY` (`D-009`), архивация до и после с разным отображением.
6. `GET /games/{id}/graph` — представление для клиента, знающего только свои состояния рёбер.

Критерии приёмки: после `READY` `DELETE` локации и перехода возвращает ошибку с указанием
причины; архивация до `READY` не видна игроку, после — видна как «выведена из игры»;
состояние ребра привязано к персонажу, тест на двух персонажей в одной локации с разными
знаниями; граф не содержит рёбер в архивированные локации для клиента.

### E05 — Медиа-ассеты

Цель: загрузить картинку, получить её по ссылке, не скомпрометировать себя.

Задачи:
1. Таблица `asset` (UUID, игра, владелец, MIME, размер, хеш, `referenced_by`),
   `FilesystemAssetStore` за интерфейсом `AssetStore`.
2. Загрузка: whitelist `jpeg/png/webp/gif`, отказ SVG и HTML (`D-074`), лимит байт,
   лимит 4096 px при декодировании (`D-076`), квота на игру и на пользователя (`D-077`).
3. Вырезание EXIF, атомарная замена (`D-077`).
4. Отдача: проверка участия (`D-075`), `nosniff`, точный `Content-Type`, `Cache-Control`.
5. ORPHAN-сборка: задача по «не упомянут ни в одной живой сущности», с сухим прогоном.

Критерии приёмки: SVG, HTML, zip с расширением `.png`, 10 МБ-PNG с 200 Мп отклонены
с разными кодами ошибок; EXIF с GPS удалён (проверка по байтам результата);
пользователь без участия в игре получает 404, а не 403 (не раскрывать существование);
орфан-сборка удаляет только незадействованные ассеты и не трогает ассет архивированного
персонажа живой игры; прерванная загрузка не оставляет полуфайл и не обнуляет предыдущий
портрет.

### E06 — Персонажи, присутствие, скрытность, перемещение

Цель: населить мир и ходить по графу.

Задачи:
1. Таблицы `character`, `occupancy`, `stealth_state`.
2. CRUD персонажей мастером: имя, портрет (ссылка на `asset`), внешность, открытая
   и закрытая история, признак играбельного/NPC.
3. Стартовое размещение, занятие персонажа игроком, освобождение мастером.
4. Скрытность: вход по разрешению мастера, выход свободный у игрока и мастера (`D-006`).
5. Перемещение по `AVAILABLE` переходу; мастер перемещает всегда.
6. События `CHARACTER_ENTERED`, `CHARACTER_LEFT`, `CHARACTER_STEALTHED`,
   `CHARACTER_REVEALED`, `CHARACTER_APPEARED_LEFT` (`D-007`).
7. Мгновенное обновление описания и инвентаря у игроков — через события, не через поллинг.

Критерии приёмки: скрытый персонаж отсутствует в ответе графа и в списках присутствующих
для другого игрока; при скрытии после публичных реплик другие видят «ушёл», реплики
остаются (тест на неизменность уже отданного ответа); игрок не может вывести из скрытности
чужого персонажа; мастер может; перемещение по закрытому переходу невозможно для игрока
и возможно для мастера; освобождение персонажа мастером снимает все его права на запись.

### E07 — Хранилища и предметы

Цель: предметы в мире, гонка за предмет без потери данных.

Задачи:
1. Таблицы `storage` (четыре типа, `D-016`), `item`, `item_placement`.
2. CRUD хранилищ и предметов мастером, признаки крупный/мелкий.
3. Перемещение: атомарная операция с `SELECT … FOR UPDATE` на предмете (`D-015`),
   отказ проигравшему как системное событие.
4. Правила: `CHARACTER_HIDDEN` недоступен чужим, `CHARACTER_VISIBLE` доступен только
   с разрешения владельца, выраженного игрой; мастер всегда (`D-017`).
5. Передача между игроками в одной локации с одинаковой скрытностью (`D-018`).
6. Видимость содержимого ровно по видимости носителя (`D-019`).
7. Сундук: описание видно присутствующим, содержимое — после открытия мастером.

Критерии приёмки: 20 параллельных попыток забрать один предмет из сундука дают ровно
один успех и 19 системных событий, в БД предмет у одного персонажа (тест с реальным
Postgres и пулом соединений); передача скрытым персонажом открытому порождает событие
передачи без раскрытия источника; скрытый персонаж не показывает крупное оружие в
ответах другим; предмет нельзя оставить вне хранилища после мутации (инвариант на
уровне сервиса + тест).

### E08 — Сообщения: типы, права, материализованная видимость

Цель: ядро системы. Самый большой набор табличных тестов в проекте.

Задачи:
1. Таблицы `message`, `inbox_entry`, `read_cursor`.
2. Пять типов (`D-031`), `assertCanPost(user, character, chat, type)` (`D-065`).
3. Вычисление получателей при записи и материализация `inbox_entry` (`D-030`).
4. `SYSTEM`-события как проекция журнала: вход/выход, правки, переходы, выдача предмета,
   запрет, разрешение хода.
5. Вход в локацию: только последнее сообщение (`D-032`) — установка курсора на текущий
   `max(seq)` плюс отдельная выдача последней реплики.
6. Ограничения (`restriction`, `D-064`): `NO_SPEECH`, `NO_ACTION`, `NO_JOKE`, `NO_MOVE`,
   причина обязательна, снятие штатно. Бан — статус участия, а не ограничение (§13).
7. Расходование бюджета хода пока только как поле события (механика — E10).
8. `on_behalf_of_master` (`D-005`).
9. Отзыв сообщений отсутствует как API (`D-008`).

Критерии приёмки: матрица прав `REQUIREMENTS §11` покрыта табличным тестом целиком,
включая отрицательные клетки; матрица видимости (скрытность × тип чата × роль ×
пошаговый режим) покрыта отдельно; ни один read-путь не читает `message` мимо `inbox_entry`
(инвариант п. 2, AST); после записи сообщения видимость уже сохранённого ответа другого
игрока не меняется (стабильность, `D-007`); навешивание `NO_SPEECH` останавливает запись
сразу, без переподключения сокета.

### E09 — Реалтайм: WebSocket, resume, двухуровневая подписка

Цель: живая доставка без потерь и утечек.

Задачи:
1. Handshake по cookie-сессии с проверкой `Origin` по allowlist (`D-073`),
   `HandshakeInterceptor` с второй реализацией на тикете (выключена).
2. Игровой канал: `{chat_id, seq, kind}` и счётчики, без текста и имени говорящего (`D-035`).
3. Канал открытого чата: тела сообщений, подписка/отписка.
4. Resume по `last_seq` одним запросом (`D-083`), дедупликация по `(chat_id, seq)`.
5. `Fanout` за интерфейсом: `InJvmFanout` + `PostgresNotifyFanout` (`D-084`),
   `NOTIFY` несёт только id события.
6. Heartbeat и высвобождение мёртвых сокетов.
7. Пересылка подписок при изменении прав (`D-065`).
8. Контракт событий: JSON-схема каждого типа, снапшот-тест.

Критерии приёмки: два клиента, разрыв соединения одного на 30 сообщений, восстановление —
получены ровно пропущенные, без дублей и потерь (тест с реальным разрывом сокета);
смена прав (персонаж снят, `NO_SPEECH`, игра `FINISHED`) приводит к отказу в записи
на уже открытом сокете без переподключения; мета-событие не содержит подстрок тела
сообщения (проверка по схеме и по фактическому payload); Origin с чужого домена отвергнут;
`InJvmFanout` и `PostgresNotifyFanout` проходят один и тот же набор тестов (контрактный
тест на двух реализациях).

### E10 — Пошаговый режим

Цель: счётчик хода как единственная механика времени.

Задачи:
1. Таблицы `turn`, `turn_budget`.
2. Флаг `turn_based`, включение и выключение мастером в любой момент (`D-012`).
3. Открытие и закрытие хода, сброс лимитов, сгорание несовершённых (`D-012`).
4. Бюджет на персонажа суммарно по чатам, кроме личного (`D-013`).
5. Сообщение мастера от лица персонажа расходует бюджет (`D-005`).
6. `JOKE`, `MASTER`, `SYSTEM` не расходуют.
7. Таймаут хода: N часов без открытия → состояние «ожидание мастера», `SPEECH` и `ACTION`
   запрещены, `JOKE` и шёпот разрешены, ничего не сгорает (`D-060`).

Критерии приёмки: персонаж в локации и в радиочате получает суммарно 1 речь и 1 действие
(тест на двойную попытку через разные чаты); мастер, написавший от лица персонажа игрока,
лишает его речи в этом ходу; переключение флага посреди игры не ломает уже записанные
сообщения; несовершённое действие не переносится; таймаут не сжигает лимиты; счётчик хода
восстанавливается из журнала (replay-тест: состояние после N событий равно состоянию,
полученному применением этих событий по одному).

### E11 — Личный чат с мастером, шёпот, радиочаты

Цель: каналы вне публичного пространства.

Задачи:
1. Личный чат с мастером per участие, автоматически при `JOINED` (`D-037`),
   подпись именем персонажа в UI мастера, выбор персонажа игроком, бюджет не расходует.
2. Шёпот: приглашение и согласие, проверка одной локации + одинаковой скрытности +
   разрешения говорить, жизнь после ухода из локации, мастер по умолчанию, `JOKE`
   разрешён (`D-038`).
3. Радиочат: фиксированный список персонажей, только `SPEECH`, отключение мастером (`D-039`).
4. Чат финального обсуждения: создание при `FINISHED`, перенос персонажей, только `JOKE`.
5. Наблюдатель исключён из личных каналов (`D-063`).

Критерии приёмки: приглашение в шёпот игроку из другой локации, с другой скрытостью или
под `NO_SPEECH` отклонено с разной причиной в каждом случае; шёпот не разрывается при
уходе участника; в радиочате `ACTION` и `JOKE` отклонены; отключённый радиочат не принимает
сообщения, но история читаема; личный чат не появляется в игровом канале другого участника;
после `FINISHED` все чаты читаемы, запись возможна только в финальный.

### E12 — Тетрадь: заметки и сохранённые сообщения

Цель: мета-слой игрока и подсветка.

Задачи:
1. Таблицы `note`, `note_keyword`, `saved_message`.
2. Заметки: автор (мастер/игрок), цель (персонаж/мастер), текст, ключевые слова.
3. Лемматизация Snowball + граница слова + флаг точного совпадения (`D-051`),
   нормализация по `D-080`.
4. Вычисление `matched_note_ids` при записи сообщения (`D-050`) и асинхронный backfill
   при создании и правке заметки с признаком `matching_pending` (`D-087`).
5. Конфликт ключей: список всех заметок (`D-052`).
6. Слияние заметок персонажей одного игрока с маркером владельца (`D-053`).
7. Сохранённое сообщение: ссылка + снимок текста и имени говорящего + комментарий (`D-055`).
8. Видимость: мастер видит заметки игроков (`D-054`), наблюдатель не видит заметок,
   сохранение сообщений ему доступно (`D-063`).

Критерии приёмки: ключ «козлоногий» подсвечивается в «с козлоногим уродом» и не
подсвечивается внутри другого слова; точный режим для имени не ловит форму косвенного
падежа; две заметки на один ключ для одного персонажа обе возвращаются клиенту;
игрок с двумя персонажами видит объединение с маркером; сохранённое сообщение не меняется
после правки мастером описания персонажа (снимок); заметка, созданная после записи
истории, подсвечивает старые сообщения после завершения backfill, а до завершения
имеет `matching_pending` и не показывает молчаливый пустой результат (`D-087`);
область backfill ограничена `inbox_entry` субъекта — проверяется счётчиком обработанных
строк на игре с двумя субъектами; AST-инвариант: нет совпадения ключевых слов в read-пути.

### E13 — Участие: приглашения, занятие, наблюдатели, пауза, архив

Цель: кто и как попадает в игру и что видит.

Задачи:
1. Приватная игра: приглашения (`INVITED` → `JOINED`/`DECLINED`), публичная — свободный вход
   после `READY`.
2. Занятие и освобождение игрового персонажа, ограничение «один игрок на слот»,
   отсутствие ограничения «один персонаж на игрока».
3. Наблюдатель: открытая часть игры и персонажей, чаты, постепенное открытие чатов
   и переходов по мере ввода в игру; видимость через `inbox_entry` с субъектом-участием
   и backfill при входе в середину игры (`D-086`).
4. `BANNED` как статус участия, а не глобальный бан.
5. Пауза с причиной (`D-059`), архивация игры (`D-010`), выход игрока с сохранением
   истории его персонажей.
6. Валидация готовности: повторная проверка при попытке `READY` после изменений.

Критерии приёмки: наблюдатель не получает закрытые истории, личные диалоги, заметки,
скрытых персонажей и неизвестные ещё переходы — проверено сравнением полного снимка
ответа; наблюдатель, вошедший в середину `RUNNING` игры, видит всю открытую историю
чатов через backfill `inbox_entry` и не имеет отдельного read-пути (`D-086`);
приглашение несуществующему пользователю и приглашение в `RUNNING` игру обработаны
по-разному; бан в игре не влияет на другие игры; пауза не меняет права, только отображение;
архивированная игра остаётся читаемой и не удаляется.

### E14 — Change set engine и заявки игроков

Цель: одна машина правок для людей и LLM.

Задачи:
1. Таблица `request` с `origin ∈ {MASTER, PLAYER, LLM}` и полным набором статусов (`D-040`).
2. Схема операций change set: `update_character_field`, `create_item`, `move_character`,
   `post_master_message`, `update_storage_contents`, `create_note` (`D-041`).
3. Применение: частичное одобрение по операциям, атомарность каждой, старое значение
   в журнале, откат.
4. Типы заявок: `CHARACTER_EDIT`, `ROLE_REQUEST`, `SLOT_QUESTION`.
5. Поле «пожелания по отыгрышу» при занятии персонажа.
6. Идемпотентность по ключу, срок жизни, автоотклонение просроченных.
7. Валидация payload по JSON-схеме до применения; невалидный = `FAILED` (`D-043`).

Критерии приёмки: заявка из трёх операций, одобрены две — применены ровно две, третья
отклонена без побочного эффекта; откат применяет старые значения из журнала; повторный
пост той же заявки с тем же ключом не создаёт дубль; заявка `PLAYER` не изменяет мир
без одобрения мастера (проверка на прямом обращении к API); параллельная заявка от
`LLM` и правка мастером одного и того же поля не теряют данные (`D-034`); replay журнала
воспроизводит состояние.

### F01 — Контур PWA: вход, список игр, кабинет

Зависимость: E03. Цель: устанавливаемое приложение с реальным входом.

Задачи: маршрут и guard, экран входа и регистрации, список игр с фильтром по
`readiness/visibility/phase`, кабинет (имя, аватар, ключи LLM — поле без использования),
service worker и manifest, базовая тема, структура i18n с русским словарём (`D-081`).

Критерии приёмки: установка в Chrome и Safari, вход после перезапуска, отсутствие
кириллических литералов вне словарей (AST-инвариант), Lighthouse PWA pass, доступность
клавиатурой на всех экранах этапа.

### F02 — Игровая комната: ленты, переходы, мастер-панель

Зависимость: E09. Цель: основной экран, на котором держится продукт.

Задачи: список чатов с бейджами из мета-канала, лента с виртуализацией и пагинацией
(`D-082`), переключение открытого чата, форма с выбором персонажа при двух присутствующих,
палитра типов сообщения, карта переходов с тремя состояниями рёбер, мастер-панель
(персонажи, перемещение, скрытность, ограничения), клавиатурная навигация (`D-085`),
офлайн-чтение кэшированной ленты.

Критерии приёмки: 10 000 сообщений в ленте — скролл 60 fps на мобильном профиле
(performance-тест в CI на фиксированном железе), виртуализация подтверждена счётчиком
узлов DOM; бейдж не учитывает скрытых персонажей и чужие личные каналы; выбор персонажа
обязателен при двух присутствующих и отсутствует при одном; закрытый переход отображается
с причиной, неизвестный — отсутствует; метрика времени до первого сообщения после
переподключения.

### F03 — Пошаговый режим и ограничения в UI

Зависимость: E10. Задачи: индикатор бюджета per персонаж, состояние «ожидание мастера»
(`D-060`), панель управления ходом, отображение ограничений с причиной и сроком.

Критерии приёмки: исчерпанный бюджет виден до попытки отправки; при таймауте хода
`JOKE` и шёпот доступны, `SPEECH` и `ACTION` заблокированы с объяснением; причина
ограничения показана игроку.

### F04 — Личные каналы и тетрадь

Зависимость: E11, E12. Задачи: личный чат с мастером, шёпот с приглашением, радиочаты,
вкладка «Заметки» и вкладка «Сохранённое», подсветка ключевых слов со списком при
конфликте (`D-052`), маркер владельца заметки (`D-053`).

Критерии приёмки: подсветка не требует клиентского поиска по тексту (только
`matched_note_ids`); конфликт ключей показывает все заметки; тетрадь сохраняется при
смене персонажа; наблюдатель видит сохранённое и не видит заметок.

### F05 — Заявки и панель мастера для LLM

Зависимость: E14. Задачи: форма предложения правки персонажа с диффом, очередь заявок
мастера, частичное одобрение по операциям, панель со-мастера и автопилота, статусы
ошибок LLM различимые пользователем (`D-043`).

Критерии приёмки: три операции в заявке, одобрение двух мышью, третья отклонена;
ошибка «кончились лимиты» показана текстом, отличным от «таймаут» и «невалидный ответ»;
при отсутствии ключа LLM опции скрыты, а не активны с ошибкой.

### O01 — Почта: подтверждение и сброс пароля

Зависимость: E02. Задачи: SMTP-адаптер `MailSender`, шаблона писем, чек-лист DNS
(SPF, DKIM, DMARC) в `docs/OPS/email.md`, rate limit и анти-enumeration под нагрузкой,
мониторинг доставки.

Критерии приёмки: письмо доходит до реального ящика в профиле `prod` на настроенном
SMTP; `mail-tester.com` ≥ 9/10 после DNS; enumeration закрыт (одинаковый ответ и
одинаковое время, проверено сравнением); прод без SMTP по-прежнему падает на старте.

### O02 — Экспорт, архив, эксплуатационные операции

Зависимость: E13. Задачи: экспорт игры (транскрипты по чатам, описания мира, персонажи,
заметки) в JSON и Markdown (`D-061`), архивация (`D-010`), dry-run ORPHAN-сборки как
операция, метрики (активные сокеты per игра, глубина очереди LLM, размер журнала).

Критерии приёмки: экспорт завершённой игры читается человеком и машиной, содержит
все чаты включая личные и закрытые истории с явной маркировкой, восстанавливается
обратно в тестовую БД; экспорт не раскрывается никому, кроме мастера (`D-021`);
архивированная игра остаётся читаемой участниками.

### O03 — Заготовка уведомлений

Зависимость: E09. Задачи: карта «событие → канал» в `notification_preference`,
фильтр событий-кандидатов (приглашение в шёпот, ответ мастера, открытие хода, выход из
скрытности, предложение предмета), dry-run отправитель, пишущий в лог.

Критерии приёмки: для каждого события из списка определён канал и текст; payload
не содержит закрытых историй и содержимого личных диалогов (`D-046`); отправка
фактически не происходит (`D-070`); добавление реального транспорта не требует
изменения журнала и inbox (проверяется ревью-чеклистом).

## 5. Риски плана

| Риск | Когда проявится | Митигация |
|---|---|---|
| Матрица видимости окажется неполной после E08 | при включении E10 или E11 | табличные тесты на список клеток, а не на код; новая клетка = новый тест до кода |
| Resume и порядок событий сломаются при переходе на `PostgresNotifyFanout` | при втором инстансе | контрактный тест на двух реализациях уже в E09 |
| Лемматизация даёт неприемлемые ложные срабатывания на именах | E12 | флаг точного совпадения в модели с первого дня (`D-051`) |
| Объём `inbox_entry` вырастет нелинейно при большом числе персонажей у игрока | E08 под нагрузкой | тест на 10 персонажей × 50 чатов в E08, а не в проде |
| Change set не покрывает какую-то правку мастера | E14 | список операций сверяется с перечнем мутаций из E03…E07 до начала кода |
| Фронт не успевает за бэком и E14 негде проверить | фаза 6 | F02 существует раньше, чем начинается E10 |
| DNS и SMTP окажутся дольше кода | O01 | заказывать домены и записи заранее, O01 не блокирует ничего |

## 6. Что нужно от владельца продукта перед E01

1. Подтвердить или заменить `D-090` (frontend-стек). Не блокирует E01…E14, нужно до F01.
2. Подтвердить, что каркас миграции в E01 включает все таблицы сразу, даже неиспользуемые.
   Это проверка модели данных на прочность, и она дешевле на этапе пустых таблиц.
3. Сказать, где будет жить прод (один инстанс? контейнер? VM?), потому что от этого
   зависит формат логов и способ развёртывания в E01, но не домен.
