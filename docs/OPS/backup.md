# Резервное копирование и восстановление

Этап `O02`. Документ описывает ежедневный бэкап, хранение, проверку восстановления и
порядок действий при потере базы. Решения: `D-101`, `D-010`, `D-061`.

Мир игры — рукописный текст мастера за месяц. Потеря базы означает потерю проекта целиком,
поэтому бэкап — обязательная процедура, а не пожелание (`D-101`). Проверка восстановления
входит в неё: непроверенный бэкап не считается бэкапом.

## 1. Что копируется

| Часть | Чем | Куда |
|---|---|---|
| База PostgreSQL | `pg_dump -Fc` | `backups/<дата>/chattergame.dump` |
| Каталог медиа | `tar -czf` | `backups/<дата>/media.tar.gz` |
| Число строк по таблицам | `psql` | `backups/<дата>/counts.txt` |
| Контрольные суммы | `sha256sum` | `backups/<дата>/SHA256SUMS` |

Комплект лежит одной папкой с датой UTC. Разделять базу и медиа по разным расписаниям
нельзя: картинки без строк и строки без картинок одинаково не восстанавливаются, а
«база от вторника, медиа от среды» — это расхождение, которое обнаруживается уже после
аварии.

Ключ шифрования LLM-креденшалов и пароль SMTP в бэкап не входят: они живут только
в окружении (`D-079`, `D-093`). После восстановления их нужно задать заново — иначе
профили с ключами расшифровать нечем.

## 2. Запуск

```bash
CHATTERGAME_DB_URL=jdbc:postgresql://db:5432/chattergame \
CHATTERGAME_DB_USER=chattergame \
CHATTERGAME_DB_PASSWORD=... \
CHATTERGAME_MEDIA_ROOT=/var/lib/chattergame/media \
CHATTERGAME_BACKUP_DIR=/var/backups/chattergame \
  ./scripts/backup.sh
```

Переменные:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CHATTERGAME_BACKUP_DIR` | `./backups` | Корень комплектов |
| `CHATTERGAME_BACKUP_RETENTION_DAYS` | `14` | Срок хранения (`D-101`) |
| `CHATTERGAME_MEDIA_ROOT` | `./data/media` | Каталог медиа |
| `CHATTERGAME_DB_URL`, `_USER`, `_PASSWORD` | локальные значения compose | База |

Клиент `pg_dump`/`pg_restore` обязан быть той же мажорной версии, что сервер (`D-092`).
Старший клиент пишет в дамп настройки, которых сервер не знает, и копия перестаёт
восстанавливаться — молча, до первой проверки. Оба скрипта сверяют версии и падают
с понятным сообщением, если они разошлись.

Расписание — ежедневно, вне часов, когда мастер обычно пишет:

```cron
15 3 * * *  cd /opt/chattergame && ./scripts/backup.sh >> /var/log/chattergame-backup.log 2>&1
```

Скрипт удаляет только собственные комплекты старше срока хранения. Чужие файлы в каталоге
бэкапов он не трогает, поэтому каталог можно держать общим с другими копиями.

## 3. Проверка восстановления

Проверка обязательна и выполняется не реже раза в неделю, а также после каждой смены
версии PostgreSQL или схемы:

```bash
CHATTERGAME_DB_URL=jdbc:postgresql://localhost:5432/chattergame \
  ./scripts/restore-check.sh backups/20260101T031500Z
```

Скрипт:

1. проверяет `SHA256SUMS` комплекта;
2. создаёт пустую базу `<db>_restore_check` и восстанавливает в неё дамп
   с `--exit-on-error`;
3. сверяет число строк в доменных таблицах (`game`, `game_event`, `message`,
   `inbox_entry`, `character`, `membership`, `note`, `item`, `storage` и другие)
   с `counts.txt` из комплекта — снимком на момент дампа, а не с боевой базой: между
   бэкапом и проверкой проходят часы, и «в боевой больше» — норма;
4. убеждается, что архив медиа читается;
5. удаляет проверочную базу.

Боевая база при проверке не изменяется. Проверочная база — временная копия, а не данные
игры, поэтому удаляется целиком; запрет `D-010` относится к доменным строкам.

Восстановление без аргумента берёт последний комплект: так проверка запускается одной
командой и не требует помнить дату.

## 4. Восстановление после аварии

1. Остановить приложение: пока оно пишет, восстановление затрёт свежие строки.
2. Создать пустую базу и восстановить дамп:

   ```bash
   createdb -h db -U chattergame chattergame
   pg_restore -h db -U chattergame -d chattergame --no-owner --no-privileges \
     backups/20260101T031500Z/chattergame.dump
   ```

3. Развернуть медиа:

   ```bash
   mkdir -p /var/lib/chattergame/media
   tar -xzf backups/20260101T031500Z/media.tar.gz -C /var/lib/chattergame/media
   ```

4. Задать секреты окружения заново: ключ шифрования LLM-креденшалов и параметры SMTP
   (`docs/OPS/email.md`). Без ключа старые ключи LLM не читаются — их придётся ввести
   заново из профиля.
5. Запустить приложение и прогнать `./scripts/restore-check.sh` на восстановленном
   комплекте: он должен дать совпадение по числу строк.
6. Открыть одну завершённую игру и сверить последние сообщения с тем, что помнит мастер.

## 5. Экспорт как вторая линия

`D-061` даёт мастеру выгрузку игры в JSON и Markdown. Это не замена бэкапу: экспорт
делается по одной игре и вручную, а бэкап — по всему узлу и по расписанию. Но у экспорта
есть свойство, которого у дампа нет: он читается человеком и переносится между базами
(`D-146`). Поэтому после завершения крупной игры мастеру стоит забрать её комплект
отдельно — он переживёт и потерю диска, и смену сервера.
